# CircleCI Dynamic Configuration – Path Filtering Parameters Fix

## 📌 Overview

While setting up CircleCI dynamic configuration using the official [Using Dynamic Configuration](https://circleci.com/docs/guides/orchestrate/using-dynamic-configuration/) guide, I encountered a critical issue where **parameters generated by path filtering were not passed to the continuation pipeline**. This caused job conditions using `<< pipeline.parameters.* >>` to always evaluate to their default values, breaking dynamic behavior.
---

## 🛑 Problem

### Symptoms

- Followed the guide exactly with `path-filtering/set-parameters`.
- Mapped parameters (e.g., `always-continue: true`) **appeared correctly** in `/tmp/pipeline-parameters.json`.
- In the **Continue Pipeline** step (Pipelines UI), `"parameters": {}` was always empty.
- `when:` conditions in `shared-config.yml`, `code-config.yml`, and `docs-config.yml` never picked up mapped values, falling back to defaults.

### Root Cause

- The `continuation/continue` example in the official guide **omits** the `parameters:` field.
- Without explicitly passing `/tmp/pipeline-parameters.json`, continuation receives an empty `{}` parameters object.

---

## 🔍 Steps to Reproduce

1. Implement the official example exactly as shown in the guide.
2. Add mappings such as:

   ```yaml
   mapping: |
     .* always-continue true
     src/.* build-code true .circleci/code-config.yml
     docs/.* build-docs true .circleci/docs-config.yml
   ```

3. Commit a file change matching one of the regex patterns.
4. Observe the **Continue Pipeline** step → `"parameters": {}` stays empty.
5. Any job conditioned with `when: << pipeline.parameters.always-continue >>` will never run unless the default in YAML is `true`.

---

## ✅ Solution

Add the missing `parameters:` field to explicitly pass the JSON parameters file from `path-filtering/set-parameters` to `continuation/continue`:

```yaml
- continuation/continue:
    configuration_path: /tmp/generated-config.yml
    parameters: /tmp/pipeline-parameters.json
```

Here:

- `/tmp/generated-config.yml` = dynamically generated config.
- `/tmp/pipeline-parameters.json` = file generated by `path-filtering/set-parameters` (default `<< parameters.output-path >>`).

---

## 🚀 Impact of the Fix

**Before the Fix:**

- Mapped parameters in `path-filtering` were never used by continuation.
- Dynamic control over workflows and jobs was impossible—only file presence/absence could influence execution.
- The `mapping` section’s parameter values were essentially ignored.

**After the Fix:**

- Parameters are **successfully passed** from `path-filtering/set-parameters` → `/tmp/pipeline-parameters.json` → `continuation/continue`.
- **MAJOR IMPACT:**

  - Developers can now pass **any number of parameters** and **map any number of files** in `mapping`.
  - These parameters can dynamically control **any workflows and jobs** in the generated pipeline.
  - This enables **true multi-parameter dynamic configuration**—previously impossible in the current guide’s setup, which only allowed file-based triggering.
  - Especially beneficial when using separate jobs (`path-filtering/set-parameters`, `path-filtering/generate-config`, `continuation/continue`) instead of the single `path-filtering/filter` workflow, as each requires parameters to be passed explicitly.

- Result: **Finer control, fewer wasted builds, full flexibility in CI/CD orchestration.**

---

## 🗂 Related Issue

Raised to CircleCI Docs: [circleci/circleci-docs#9480](https://github.com/circleci/circleci-docs/issues/9480) – Requesting correction in the official how-to guide.

If you use **path filtering with dynamic continuation**, always **pass parameters explicitly**—otherwise they’ll default to `{}`, and you’ll miss out on the full power of CircleCI’s dynamic configuration.
